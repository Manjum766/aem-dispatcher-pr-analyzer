1. Overview & Pipeline Architecture

On every pull request (opened, synchronize, reopened) against this repository, four GitHub Actions jobs run in parallel and then consolidate results into a single upserted PR comment.

3. Job 1 — Dispatcher Rules Lint

Script: .github/scripts/dispatcher_analyzer.py

Scans all .any, .vhost, and .farm files under dispatcher/src/. Emits GitHub Actions inline annotations (::error file=…,line=…::) that appear directly on changed lines in the PR Files tab.

Directory layout scanned

PathFile typeRules checked
dispatcher/src/conf.dispatcher.d/filters/*.anyDISP-001, DISP-002, DISP-003, DISP-004
dispatcher/src/conf.dispatcher/ (flat fallback)*.anyDISP-005, DISP-008, DISP-009, DISP-010, DISP-005b
dispatcher/src/conf.d/available_vhosts/*.vhostDISP-006, DISP-007, DISP-GQL
dispatcher/src/conf.dispatcher.d/enabled_farms/*.farmDISP-008

Fail / pass logic

The script calls sys.exit(1) when any finding has severity CRITICAL or HIGH, failing the dispatcher-lint job and blocking the merge. Artifacts (dispatcher-result.json, dispatcher-report.md) are uploaded with if: always() so they persist even on failure.

Risk score

SeverityScore weight
CRITICAL40 points
HIGH25 points
MEDIUM10 points
LOW5 points

Score is capped at 100. Level: 0 = CLEAN, <25 = LOW, <50 = MEDIUM, <75 = HIGH, ≥75 = CRITICAL.

5. Job 3 — Snyk SAST + Dependency CVEs

Two scan modes

CommandOutput formatWhat it finds
snyk code test --sarif-file-output=snyk-code-raw.json .SARIFJava SAST: SQL injection, hardcoded passwords, weak Random, NPE — uses level: error/warning/note
snyk test --file=java-demo/pom.xml --json-file-output=snyk-maven-raw.jsonJSON (vulnerabilities[])CVEs in jackson-databind 2.9.8, commons-collections4 4.0, spring-web 5.2.0
Critical bug that was fixed: The old command used --json (stdout) and --all-projects together with --file=. These flags conflict — Snyk ignores --file= when --all-projects is set, finds no manifest at repo root, and its error output overwrites the JSON file. Use --json-file-output= instead which writes to a separate file.

SARIF severity mapping

Snyk SAST outputs SARIF where severity is expressed as level, not severity. The merge script maps them:

SARIF levelMapped to
errorhigh
warningmedium
notelow

Secrets detection

Matched against ruleId in SARIF results. Keywords: secret, credential, password, hardcoded, token, apikey. The old approach stringified the entire result object — unreliable and produced false negatives.

Fail logic

failed = total_secrets > 0 or dep_critical > 0 or total_high > 0

Where total_high = code_high (SAST) + dep_critical + dep_high (CVEs).

6. Job 4 — Post PR Comment

Runs with needs: [dispatcher-lint, sonarcloud-scan, snyk-scan] and if: always() — executes even when upstream jobs fail. Downloads all three artifacts, builds a consolidated Markdown comment, and upserts it using the GitHub REST API.

Upsert logic

The comment body contains a hidden marker <!-- pr-review-agent-marker -->. On each run, the script fetches existing comments, finds one containing the marker, and PATCHes it. If none exists, it POSTs a new comment.

Graceful degradation

Each result file is loaded with a try/except that returns {"status": "did_not_complete"} if the file is missing — so the comment always posts even if one scan failed entirely.

10. Permissions Model

Workflow-level permission is contents: read only. Each job is granted the minimum it needs:

JobpermissionsReason
dispatcher-lintcontents: readCheckout only
sonarcloud-scancontents: read
statuses: write		Quality Gate action posts a commit status
snyk-scancontents: readCheckout only
post-commentpull-requests: writeCreates / updates the PR comment
Why this matters: The old workflow granted pull-requests: write and statuses: write at workflow level, meaning third-party actions (Snyk CLI, SonarSource actions) ran with write access to PRs and commit statuses. Job-level permissions scope each permission to only the job that needs it.

11. Branch Protection Setup

The workflow jobs fail with exit code 1 on findings, but the merge button only locks if you configure required status checks:

  1. Go to Settings → Branches → Add branch protection rule for main (or master)
  2. Enable "Require status checks to pass before merging"
  3. Add these three checks:
    • Dispatcher Rules Lint
    • SonarCloud Scan
    • Snyk Scan
  4. Enable "Require branches to be up to date before merging"

13. Bugs Fixed During Development

Bug 1 — SonarQube job was commented out but steps were orphaned

The sonarqube-scan: job header and its Checkout step were commented out, but the remaining steps (Scan, Quality Gate, Upload) were not. They silently ran inside dispatcher-lint with no compiled Java, scanned nothing, and reported clean.

Fix: Restored the full sonarcloud-scan: job as a proper top-level job.

Bug 2 — sonar-project.properties pointed at non-existent paths

sonar.sources=core/src/main/java — the core/ directory does not exist. Sonar scanned zero files and reported zero issues.

Fix: Changed all paths to java-demo/src/main/java, java-demo/target/classes, etc.

Bug 3 — Quality Gate failure was swallowed

continue-on-error: true on the Quality Gate step meant a FAILED gate produced a green ✅ check.

Fix: Removed continue-on-error. A failed gate now fails the job.

Bug 4 — Snyk SARIF severity fields were parsed as CVE format

snyk code test outputs SARIF where severity is level: "error", not severity: "critical". The old code called count_sev(code, "critical") which always returned 0.

Fix: Added dedicated SARIF parser with level→severity mapping (error→high, warning→medium, note→low).

Bug 5 — --all-projects + --file= conflict in Snyk

snyk test --file=java-demo/pom.xml --all-projects — these flags conflict. Snyk ignores --file=, finds no manifest at repo root, and its error message overwrites the JSON output file.

Fix: Removed --all-projects. Changed to --json-file-output=snyk-maven-raw.json which writes JSON to a separate file, keeping stderr/stdout clean.

Bug 6 — Cache file rules not checked for sensitive paths

The analyzer had rules for /crx/* and /system/* only in filter files (checking /url patterns). In this repo the only config file is a cache file using /glob patterns — none of those rules ever fired.

Fix: Added DISP-009 and DISP-010 to check_cache_file() that scan /glob allow lines for sensitive paths. Added DISP-008 check to cache files (it was only in check_farm_file()).

Bug 7 — sonar.projectKey used shell variable syntax

sonar.projectKey=${SONAR_PROJECT_KEY} — sonar-scanner does not expand shell variables in properties files. The literal string ${SONAR_PROJECT_KEY} was sent as the project key, matching nothing on SonarCloud.

Fix: Hardcoded the literal value: sonar.projectKey=aem-dispatcher-pr-analyzer. Added required sonar.organization=aem-dispatcher-pr-analyzer (mandatory for SonarCloud).

Bug 8 — Permissions granted at workflow level

pull-requests: write and statuses: write were at workflow level, granting write access to all jobs including third-party actions.

Fix: Moved to job-level permissions. Workflow default is contents: read only.

Bug 9 — Dispatcher job never exited non-zero

The Python script computed status: "failed" in the JSON but always exited 0 — GitHub showed a green check even with CRITICAL findings.

Fix: Added sys.exit(1) at the end of the script when status == "failed".
